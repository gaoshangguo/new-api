# 渠道密钥加密与轮换

## 加密存储

- 渠道密钥使用 AES-256-GCM 加密落库（密文前缀 `enc:v1:`），读取时自动解密。
- 主密钥解析顺序：`CHANNEL_KEY_MASTER_KEY`（**恰好 32 字节**，其他长度会被忽略并告警回退）→ 数据目录持久化文件 `channel-key-master.key`（首次启动生成 32 随机字节、0600 权限；容器数据卷 `/data` 下，重启/重建容器均保留）→ `sha256(CRYPTO_SECRET||SESSION_SECRET)` 派生兜底（此路径启动时 SysError 告警）。生产环境必须设置独立 `CHANNEL_KEY_MASTER_KEY`，否则启动日志会告警。
- 存量明文密钥在启动时自动迁移（幂等）；任何一次渠道更新也会单独迁移该条。
- 密钥不写日志：查看密钥仍需二次安全验证并留审计；解密失败一律 fail-closed（该渠道 Key 置空并告警，绝不静默返回错误），余额查询等外部请求的错误文本经脱敏剥离 URL/查询参数，不会携带密钥。

## 密钥到期提醒

- 渠道表单可设置「密钥到期时间」；系统任务 `channel_key_expiry` 默认每 6 小时扫描，
  在到期前 7 天提醒 Root（`CHANNEL_KEY_EXPIRY_TASK_ENABLED`、`CHANNEL_KEY_EXPIRY_ADVANCE_DAYS` 可配）。
- 同一渠道 24 小时内不重复提醒。

## 主密钥轮换流程

1. 备份数据库（账务与审计表单独备份）。
2. 设置新密钥：`CHANNEL_KEY_MASTER_KEY=<新密钥>`，并保留旧密钥：
   `CHANNEL_KEY_MASTER_KEY_PREVIOUS=<旧密钥>`。
3. 重启服务（重启期间旧密文仍可解密，不中断业务）。
4. 执行重加密任务：POST /api/system-task/channel-key-re-encrypt（Root 权限），
   全部渠道密钥切换到新主密钥。
5. 确认任务成功后移除 `CHANNEL_KEY_MASTER_KEY_PREVIOUS` 并重启。
6. 抽样验证渠道可用、日志无明文。

警告：主密钥丢失将导致全部渠道密钥不可恢复。请先备份，再轮换。

## 主密钥备份

- 主密钥是密文的唯一恢复手段，必须与数据库一起备份：
  - 使用持久化文件模式（未设置 env）时，`channel-key-master.key` 与数据库同卷存放，
    备份数据库时必须连同该文件一同备份（同卷快照即可）；
  - 生产环境建议直接配置 `CHANNEL_KEY_MASTER_KEY` env 并纳入配置/密钥管理备份，
    此时文件模式不再参与解析（仍会生成但被忽略，可留作兜底）。
- 恢复流程：先恢复数据库备份，再恢复同名主密钥文件（或设置同一 env），密文才能解密。

## 重加密任务统计口径

- 任务结果返回 `total / re_encrypted / failed` 三个数字：
  - `total`：全表渠道数（含解密失败 fail-closed 后 Key 已被置空的渠道）；
  - `re_encrypted`：成功解密并重新加密保存的渠道数；
  - `failed`：解密失败、加密失败或保存失败的渠道数。
- 注意：因 AfterFind 钩子解密失败会将 Key 置空（fail-closed），这类渠道计入 `total`，
  **不计入 `failed`**，也不会被重加密（空 Key 直接跳过）。若 `total` 大于
  `re_encrypted + failed`，差额即为解密失败的渠道——需检查主密钥是否正确
  （对应渠道 id 的解密告警见服务日志 `channel %d key decrypt failed`），
  并评估是否通过 `CHANNEL_KEY_MASTER_KEY_PREVIOUS` 回退恢复。
